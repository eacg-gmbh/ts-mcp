# Architecture

## System Overview

TrustSource MCP Server (`ts-mcp`) exposes the TrustSource REST API v2 as a set of domain-grouped MCP tools, allowing LLM agents (Claude, etc.) to interact with TrustSource for SBOM management, compliance checks, vulnerability tracking, and risk management.

## Components

### MCP Server (`src/index.ts`)

Entry point. Loads configuration, validates the API key against TrustSource, registers domain tools filtered by the configured access mode, and connects via the configured transport (stdio or Streamable HTTP).

### Configuration (`src/config.ts`)

Reads environment variables:
- `TS_API_KEY` (required) — TrustSource API key
- `TS_ACCESS_MODE` — `read` | `readwrite` | `full` (default: `read`)
- `TS_ROLE` — `compliance-manager` | `security-manager` | `component-manager` (default: `compliance-manager`); selects the role pack, see ADR-012
- `TS_TRANSPORT` — `stdio` | `http` (default: `stdio`)
- `TS_HTTP_PORT` — HTTP listen port (default: `3000`, only used with `http` transport)
- `TS_API_BASE_URL` — API base URL (default: `https://api.trustsource.io/v2`)
- `TS_LOG_LEVEL` — `debug` | `info` | `warn` | `error` (default: `info`)

Implements access mode hierarchy: `read < readwrite < full`.

### API Client (`src/api-client.ts`)

HTTP client wrapping `fetch` for the TrustSource API. Handles:
- API key injection via `x-api-key` header
- Query parameter construction
- JSON request/response serialization
- Startup key validation

### Input Validation (`src/validation.ts`)

Defensive validation layer between LLM input and API calls:
- ID parameters: alphanumeric + limited special chars, max 256 chars
- String parameters: max 10,000 chars, no control characters, no injection patterns
- JSON bodies: max 5 MB, well-formed JSON
- SBOM documents: structural validation for CycloneDX (bomFormat, specVersion) and SPDX (spdxVersion, SPDXID)

### Generated Tools (`src/generated-tools.ts`)

Auto-generated by `scripts/codegen.ts` from:
- `ts-api/openapi.yaml` — canonical API specification
- `domain-mapping.yaml` — domain grouping, descriptions, and access levels

Each domain tool bundles related API operations as "actions" with a shared input schema.

### Role Packs (`src/roles/<role>/`)

Everything that varies by `TS_ROLE` (ADR-012): a charter (`charter.ts`) and, where
built, playbooks exposed as MCP prompts (`prompts.ts`), wired together in the pack's
`index.ts` against the shared `RolePack` interface (`src/roles/types.ts`).
`compliance-manager` ships the full pack — eleven MCP prompts encoding the recurring
procedures of a compliance manager, each with a fixed evidence path, explicit
decision rules and a defined deliverable, playbook text adapting to the configured
access mode and project scope at registration time. `security-manager` and
`component-manager` currently ship a charter only. `src/roles/shared-authority.ts`
holds the read/readwrite/full authority language every charter shares.
`src/roles/compliance-manager/ledger.ts` holds the `ledger` argument's rendering
logic, shared across every trigger-context playbook (ADR-013).

### Playbooks and Role Charter dispatch (`src/prompts.ts`, `src/resources.ts`)

Thin dispatchers: they look up the active role pack for `config.role` (`src/roles/
index.ts`'s `ROLE_PACKS`) and delegate to it. `resources.ts` also owns the two
resources that are the same for every role — the compliance policy and the mandate
scope — registering the role charter itself from the pack's own `buildCharter`. The
charter is assembled from the configuration so that the stated authority always
matches the enforced one.

### Policy Pack (`src/policy.ts`)

The FOSS policy the agent decides against — licence classification, obligations,
vulnerability exposure classes with per-class SLAs, VEX vocabulary, escalation paths.
Built-in default, overridable via `TS_POLICY_FILE`. Reading a configured policy file
is fail-fast: an unreadable file aborts startup.

### Code Generator (`scripts/codegen.ts`)

Reads OpenAPI spec and domain mapping, validates all mapped paths exist in the spec, warns about unmapped paths, and emits typed TypeScript tool definitions. Run via `npm run codegen`.

## Transport Modes

The server supports two transport modes, selected via `TS_TRANSPORT`:

### stdio (default)

Standard MCP stdio transport. The server communicates over stdin/stdout and handles a single session. Use for local development and direct MCP client integration (Claude Desktop, Claude Code).

### Streamable HTTP

Multi-session HTTP transport following the MCP Streamable HTTP specification. Each client session receives a unique `Mcp-Session-Id` header. Sessions are isolated and managed independently.

- `POST /mcp` — MCP JSON-RPC messages (new sessions are created automatically)
- `GET /health` — Health check endpoint (returns `{"status":"ok","version":"..."}`)

Suitable for server deployment (ECS, Kubernetes) where multiple clients connect concurrently.

## Deployment

Docker image with multi-stage build (build + runtime). npm/yarn/corepack are removed from the runtime image to minimize the attack surface.

**Local (stdio):**
```
docker run -i --rm -e TS_API_KEY=xxx trustsource/ts-mcp
```

**Server (Streamable HTTP):**
```
docker run -p 3000:3000 -e TS_API_KEY=xxx -e TS_TRANSPORT=http trustsource/ts-mcp
```

### Recommended: Internal Load Balancer

For production server deployments, we recommend placing the MCP server behind an internal application load balancer:

```
Internal clients (VPC only)
        │
        ▼  private DNS (e.g. mcp.internal)
  ┌──────────────┐
  │ Internal ALB  │ ◄── ingress restricted to known consumer security groups
  │ (port 80/443) │
  └──────┬───────┘
         │ target group :3000
         ▼
  ┌──────────────┐
  │  ECS Fargate  │ ◄── ingress only from ALB security group
  │  (MCP Server) │ ──► egress HTTPS to TrustSource API
  └──────────────┘
         │
         │ API key from secrets manager
         ▼
  TrustSource REST API
```

This provides a triple security barrier:
1. **DNS resolution** — private hosted zone, only resolvable within the VPC
2. **ALB ingress** — security group permits only known consumer groups
3. **Task ingress** — ECS task security group accepts only traffic from the ALB

API keys should be stored in a secrets manager (e.g. AWS Secrets Manager) and injected at runtime, never passed as stack parameters or environment variables in config files.

## Update Flow

```
TrustSource OpenAPI Repo
        │ (GitHub Action: detect spec change)
        ▼
ts-mcp Repo: updated openapi.yaml
        │ (CI: npm run codegen → diff)
        ▼
PR with updated generated-tools.ts
        │ (merge)
        ▼
GitHub Action: Docker build + push to Docker Hub
```

The domain-mapping.yaml file controls which API paths are included and how they are grouped. New endpoints not covered by an existing mapping entry will cause the codegen to emit a warning; new endpoints that match no domain will break the build intentionally to force a mapping update.

## Architecture Decision Records

### ADR-001: Domain-based tool grouping (2026-06-03, v0.1.0)

**Context:** MCP tools map 1:1 to LLM tool selection. The TrustSource API has ~84 operations. Exposing each as a separate tool degrades LLM tool selection quality.

**Decision:** Group operations by business domain (~16 tools), each with an `action` parameter to select the specific operation.

**Consequences:** Better LLM performance in tool selection. Slightly more complex input schemas per tool. Action names must be unique within a domain.

### ADR-002: Server-side access mode configuration (2026-06-03, v0.1.0)

**Context:** Users need to restrict what the LLM can do (read-only vs. full access). Options considered: separate read/write tools (doubles tool count), per-tool MCP permissions, server-side config.

**Decision:** Single environment variable `TS_ACCESS_MODE` with three tiers: `read`, `readwrite`, `full`. Tools and actions are filtered at registration time. Actions requiring higher access than configured are not exposed to the LLM.

**Consequences:** Simple deployment configuration. Defense in depth with TrustSource's own role-based API keys. Tool count stays minimal. Access mode changes require container restart.

### ADR-003: Codegen from OpenAPI spec (2026-06-03, v0.1.0)

**Context:** The TrustSource API evolves. Manual tool maintenance creates drift risk. Fully dynamic (runtime parsing) adds startup complexity and makes the tool schema opaque.

**Decision:** Build-time code generation from OpenAPI spec + domain-mapping.yaml. The mapping file is the human-controlled layer; the spec is the source of truth for parameters and descriptions.

**Consequences:** Deterministic, auditable tool definitions. Unmapped paths produce warnings/errors. Update flow is: spec change → codegen → review → merge → Docker build.

### ADR-004: Input validation and startup guards (2026-06-03, v0.1.0)

**Context:** LLM agents generate unpredictable inputs. The TrustSource API validates server-side, but passing unsanitized input from an LLM creates injection risk (regex in IDs, malformed SBOMs, oversized payloads). Rate limiting is handled server-side by TrustSource (all calls are API-key-scoped), so no client-side throttling is needed.

**Decision:** Validate all inputs before forwarding to the API:
- ID/path parameters: alphanumeric + limited special chars only, max 256 chars
- String parameters: max 10,000 chars, reject control characters and injection patterns (template literals, nested brackets)
- JSON bodies: max 5 MB, well-formed JSON required
- SBOM imports: structural validation (CycloneDX: bomFormat + specVersion; SPDX: spdxVersion + SPDXID)
- API key is validated against `/account/authorization` on startup; server exits with a clear error on 401/403

**Consequences:** Defense in depth — malformed input is rejected before reaching TrustSource. Startup fails fast on invalid credentials. No client-side rate limiting simplifies the implementation while TrustSource's server-side limits remain authoritative.

### ADR-005: Streamable HTTP transport for server deployment (2026-06-07, v0.2.0)

**Context:** The initial stdio transport only supports a single local session. For server deployment (ECS, Kubernetes), the server needs to handle multiple concurrent clients over the network.

**Decision:** Add Streamable HTTP transport as an alternative, selected via `TS_TRANSPORT=http`. Each client session gets a unique `Mcp-Session-Id`. Sessions are isolated — each creates its own `McpServer` instance with independently registered tools. A `/health` endpoint supports load balancer health checks. The server listens on a configurable port (`TS_HTTP_PORT`, default 3000).

**Consequences:** The server can be deployed as a shared service behind a security group that restricts access to authorized consumer groups. Multiple LLM agents can connect concurrently. Session state is in-memory (minimal — no caching), so horizontal scaling is straightforward. stdio remains the default for local/CLI use.

### ADR-006: ts-scan quality gate before Docker Hub publish — SUPERSEDED by ADR-007 (2026-06-03, v0.1.0)

**Context:** The MCP server is distributed as a Docker image. Publishing an image with known vulnerabilities undermines TrustSource's own value proposition. Since v1.7.0, ts-scan supports `upload --wait-for-analysis --exit-on-vulns --exit-on-legal` which blocks until TrustSource completes its analysis and returns a non-zero exit code on findings.

**Decision:** The Docker publish workflow builds the image locally first, scans it with `ts-scan scan --use-syft`, uploads the scan to TrustSource with `--wait-for-analysis --exit-on-vulns --exit-on-legal --Werror`, and only pushes to Docker Hub if the analysis passes clean. The scan results are stored in the TrustSource project `ts-mcp`.

**Consequences:** No Docker image is published with known vulnerabilities or legal issues. The publish step depends on TrustSource API availability (mitigated by `--wait-timeout 300`). Adds ~2-5 minutes to the publish pipeline. Uses the organization's `TRUSTSOURCE_API_KEY` secret.

### ADR-007: Remove --exit-on-legal from quality gate (2026-06-07, v0.2.0)

**Context:** The initial quality gate used both `--exit-on-vulns` and `--exit-on-legal`. Legal warnings (unresolved obligations) blocked the Docker publish even when they were informational and not actionable without manual compliance review.

**Decision:** Remove `--exit-on-legal` from the ts-scan upload step. Keep `--exit-on-vulns --Werror` to block on vulnerability findings. Legal compliance is handled through the TrustSource approval workflow, not the CI gate.

**Consequences:** The publish pipeline only blocks on vulnerability findings. Legal compliance remains visible in TrustSource but does not prevent image publication.

### ADR-008: Ship the role, not just the tools (2026-09-21, v0.3.0)

**Context:** With 16 domain tools an agent can do anything the TrustSource API allows,
but it has no assignment. Every customer would have to write their own prompts, and
two runs a month apart would not be comparable. Options considered: leave role design
to the customer, build a separate hosted agent product, or ship the role with the
server using MCP's own prompt and resource primitives.

**Decision:** Ship the role inside the MCP server. Ten playbooks as MCP prompts, and
three resources (role charter, compliance policy, mandate scope). Playbooks and
charter are assembled from the runtime configuration, so the authority the charter
states is the authority the server enforces. The role is defined as an *organising*
one — completing notice files, resolving components, bringing legal decisions to a
conclusion and chasing owners — with vulnerability triage explicitly secondary.
Projects ship or do not ship on their legal position.

**Consequences:** The role works in any MCP client without extra infrastructure, and
it is versioned and reviewed with the server. Playbook quality becomes a product
concern rather than a customer concern. The server is no longer policy-neutral — it
carries a default policy that customers are expected to replace. An autonomous,
scheduled agent runtime can reuse the same playbooks rather than reimplementing them.

### ADR-009: Compliance policy travels with the server (2026-09-21, v0.3.0)

**Context:** The agent must decide against the organisation's policy, not against
general best practice. TrustSource's API exposes the FOSS liaison contact via
`/compliance/company/foss` but not the governing policy document; policies typically
exist as prose documents (PDF/DOCX) that are not machine-readable.

**Decision:** Carry a structured policy pack as an MCP resource — built-in default,
overridable via `TS_POLICY_FILE`. Reading a configured policy file is fail-fast: if
the file cannot be read the server exits rather than falling back to the default,
which would let the agent decide against the wrong rules while operators believe
their own policy applies.

**Consequences:** Customer onboarding gains an explicit step: translate the existing
policy document into the policy pack. That step is also where implicit rules get made
explicit, which is valuable on its own. The policy pack is a second source of truth
next to TrustSource's own project settings — they can drift, so the policy pack
records its version and review cycle. Should the API later expose policies directly,
the resource can read from the API instead without changing the playbooks.

### ADR-010: Server-enforced project scope (2026-09-21, v0.3.0)

**Context:** A TrustSource API key is company-scoped. An agent given a key for a
single project's compliance work can read the whole account. For a customer pilot on
one project this is both a trust obstacle and an unnecessary exposure.

**Decision:** `TS_PROJECT_SCOPE` binds the server to named projects. Project-addressed
operations must target a scoped project; the project ID is injected when exactly one
project is in scope; project listings are filtered to the scope; and account-wide
operations that cannot be narrowed (dashboard report, CVE impact report, scan list,
product list, user statistics) are withheld while a scope is set. An operation whose
project parameter is optional and left empty is rejected rather than allowed through
unfiltered when the scope names more than one project — there is no single ID to
inject automatically, and letting it through would return every project in the
account.

**Consequences:** A scoped server cannot enumerate out-of-scope projects or modules,
so out-of-scope IDs cannot be discovered through it. Enforcement lives in the server,
where it is auditable, rather than in prompt instructions the model may ignore. It
complements but does not replace a narrowly scoped API key — a compromised server
process still holds a company-scoped key. Withheld account-wide reports are a
deliberate trade: cross-project impact analysis requires an unscoped deployment. A
multi-project mandate cannot batch-list resources by an optional project filter in
one call; the agent must address each scoped project explicitly.

### ADR-011: Reconcile licence report against parts list (2026-09-21, v0.3.0)

**Context:** The licence report (`/core/reports/licenses`) and the parts list
(`/core/projects/{id}/partsList`) describe the same project but aggregate differently.
On a reference project the report showed 17 components under an "unknown" licence
while the parts list contained 2 components with no resolvable licence entry. An agent
trusting either number in isolation either invents work or misses it.

**Decision:** Every legal playbook reconciles both sources explicitly and treats the
parts list as the addressable truth — only named components can be acted on. The
discrepancy is reported rather than resolved silently in favour of the larger figure.

**Consequences:** Assessments are reproducible and defensible in an audit. Playbooks
are more verbose. If the two endpoints are aligned in a future API version, the
reconciliation step becomes a cheap no-op rather than wrong.

### ADR-012: `TS_ROLE` role selection and role-pack structure (2026-09-29, v0.4.0)

**Context:** ADR-008 shipped one role — Compliance Manager — hard-wired into
`src/prompts.ts`/`src/resources.ts`. `ts-agent-svc` (the standing-mandate runtime
built on top of this server, see its own ADR-004: templates map 1:1 to ts-mcp
roles) needs two more: Security Manager (vulnerability posture, CVE triage,
VEX, release gate) and Component Manager (component hygiene — metadata,
EOL, duplicate modules, upgrade candidates). Hard-wiring a second role the
same way would mean forking `prompts.ts`/`resources.ts` per role, with no
shared structure and every future role repeating the same charter/playbook
wiring from scratch.

**Decision:** `TS_ROLE=compliance-manager|security-manager|component-manager`
(default `compliance-manager`, unknown value fails fast at startup — the same
treatment `TS_ACCESS_MODE`/`TS_TRANSPORT` already get). Each role is a
self-contained pack under `src/roles/<role>/{charter.ts, prompts.ts, index.ts}`
implementing a common `RolePack` interface (`buildCharter`, optional
`registerPlaybooks`); `src/resources.ts` and `src/prompts.ts` become thin
dispatchers that look up the active pack by `config.role` and delegate to it,
keeping only what's genuinely role-independent (the compliance-policy and
mandate-scope resources) themselves. The `trustsource://role/<role>` URI is
parameterised by the selected role, so the default role's URI
(`.../compliance-manager`) is unchanged. Security Manager and Component
Manager ship as stub packs — charter only — until their playbooks are built
(tracked separately); a stub pack simply omits `registerPlaybooks`.

**Consequences:** Adding a role is now "write a role pack", not "extend two
1000-line switch-shaped files" — `ts-agent-svc`'s Security Manager and
Component Manager templates can each be pointed at a real pack as its
playbooks are built, without touching the Compliance Manager pack. The
read/readwrite/full authority language moved to a small shared module
(`src/roles/shared-authority.ts`) so it can't drift between role charters.
Existing behaviour with no `TS_ROLE` set is unchanged — verified byte-for-byte
against the pre-refactor charter output.

### ADR-013: Trigger-context arguments and ledger snapshot (2026-09-29, v0.5.0)

**Context:** `ts-agent-svc` (ADR-004/its own ADR set) dispatches a playbook whenever
a webhook fires, carrying the triggering event's own fields — project, release,
module, analysis, CVE list, approval, task — under its `TsWebhookPayloadSchema`
naming. Before this change every playbook that could use that context declared its
own ad-hoc argument (`project`, `scan_id`, `approval_id`, `release`, …), so the
runtime had to remap its payload's field names per playbook rather than passing the
trigger straight through. Separately, the runtime keeps a ledger of this agent's
standing work (open objectives, todos, what it's waiting on) that a playbook has no
way to see — every run started cold, re-deriving state the runtime already tracked.

**Decision:** every trigger-eligible playbook accepts one shared argument object,
`TRIGGER_CONTEXT_ARGS` (`src/roles/compliance-manager/prompts.ts`): `projectId`,
`releaseId`, `moduleId`, `analysisId`, `cveIds`, `approvalId`, `taskId` — named to
match `ts-agent-svc`'s own webhook payload fields exactly — plus `ledger`, a JSON
string the calling runtime renders from its own ledger state. All MCP prompt
arguments are plain strings on the wire, so `ledger` is JSON-in-a-string rather than
a structured argument; ts-mcp defines its own expected shape for it
(`LedgerSnapshot` in `src/roles/compliance-manager/ledger.ts`) rather than importing
`ts-agent-svc`'s schemas — the two repos stay independently versioned, and a caller
that isn't `ts-agent-svc` can still supply an ledger. `renderLedgerSnapshot()` turns
that argument into a markdown section every playbook interpolates near the top of
its text (open objectives, open todos, waiting-for items, a one-line "since your
last activation" summary); a missing or empty argument renders nothing, and
malformed JSON is reported in the output rather than thrown. Every trigger-context
playbook now closes with `LEDGER_UPDATES_SECTION`, a fixed instruction to report
objective/todo changes in a structured shape the runtime's `ledger_update` tool can
consume directly, instead of parsing them out of free-form prose. A playbook that
doesn't use a given field (`follow-up` never reads `cveIds`) simply ignores it — the
runtime always passes the same shape and never has to know which subset a
particular playbook cares about.

**Consequences:** `ts-agent-svc` can dispatch its own trigger payload into any
playbook without a translation layer, and a playbook gains "what have I already
started" for free instead of re-discovering it from TrustSource state on every run.
The `ledger` contract is ts-mcp's own — a breaking change to it is a ts-mcp semver
event, not something that silently drifts with `ts-agent-svc`'s internal ledger
schema. The four playbooks with no natural trigger event (`resolve-components`,
`notice-file`, `document-findings`, `stakeholder-digest`) were deliberately left on
their pre-existing `project` argument — they're invoked mid-workflow by another
playbook or by a human, not by a runtime dispatch, so there's no trigger payload to
carry. This ADR also introduces the **`new-release`** playbook: the entry point when
a release cycle opens, reconciling against the previous release's state (via the
`ledger` argument and `releases`/`risks` evidence) and proposing this cycle's
objective set — the counterpart to `release-readiness`, which gates the cycle's exit
rather than opening its entry.

## Event-Driven Operation

The pilot deployment is triggered by TrustSource's **scan-uploaded** webhook. A scan
upload starts an analysis; when it completes, the compliance manager picks the result
up and works it.

```
ts-scan upload / CI pipeline
        │
        ▼
TrustSource analysis completes
        │  webhook: scan uploaded (ts-agent-svc's trigger payload → TRIGGER_CONTEXT_ARGS)
        ▼
  Agent runtime (Agent SDK)
        │  invokes the `new-analysis` playbook, passing the event's own fields plus
        │  a `ledger` snapshot of this agent's open objectives/todos (ADR-013)
        ▼
  MCP Server (scoped to the project)
        │
        ├─► resolve-components ──► deep scan ──► licence + copyright established
        ├─► notice-file       ──► obligation register, gaps, owners
        ├─► legal-decisions   ──► approval request opened with a complete dossier
        └─► follow-up         ──► drafted reminders, escalations
                │
                ▼
        Risk register (the agent's memory) + drafted messages for a human to release
                │
                ▼
        Ledger update proposal (LEDGER_UPDATES_SECTION) → runtime's `ledger_update` tool
```

The risk register doubles as the agent's state store: each run reads what was already
decided before deciding anything. No separate agent database is required, and the
state stays where auditors and humans already look. The ledger snapshot (ADR-013)
complements this for state that isn't TrustSource's to hold — cross-run todos and
waiting-for items that live in the runtime, not in a TrustSource record.

A release cycle follows the same pattern at its two ends: a **release-opened** event
invokes `new-release` to plan the cycle, and the cycle's exit invokes
`release-readiness` to gate it.

Scheduled runs (a weekly `follow-up`, a `release-readiness` gate in CI) use the same
playbooks — the runtime invokes MCP prompts rather than reimplementing the procedures.

## CI/CD Pipeline

```
Push to main / tag v*
        │
        ▼
CI: Build & Validate (ci.yaml)
        │ npm ci → codegen → diff-check → tsc build
        │
        ▼
Docker: Build local image (docker-publish.yaml)
        │
        ▼
ts-scan: Scan image with Syft backend
        │ ts-scan scan --use-syft docker:trustsource/ts-mcp:scan-candidate
        │
        ▼
ts-scan: Upload to TrustSource & wait for analysis
        │ --wait-for-analysis --exit-on-vulns --exit-on-legal --Werror
        │
        ├── PASS → Push to Docker Hub (tagged by version/branch/sha)
        │
        └── FAIL → Pipeline aborts, no publish
```

Weekly: `sync-openapi.yaml` checks for upstream OpenAPI spec changes and creates a PR if the spec has been updated.
